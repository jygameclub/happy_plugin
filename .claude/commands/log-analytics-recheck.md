# 游戏日志复查分析 /log-analytics-recheck

基于已有日志进行深度复查分析，验证修复效果，无需重新下载日志。

## 设计原则

1. **全 Agent 执行** - 所有 Phase 通过 Task 工具调用 agent
2. **支持重复执行** - 每次执行生成唯一文档，不覆盖历史
3. **superpowers 集成** - 使用 superpowers:writing-plans 生成执行文档
4. **跳过下载** - 直接使用 logjson/ 目录现有日志
5. **对比分析** - 与上次分析结果对比，检查修复效果

## 适用场景

| 场景 | 说明 |
|------|------|
| 修复验证 | 执行修复后，验证问题是否解决 |
| 深度分析 | 首次分析后，进行更细致的检查 |
| 回归测试 | 代码变更后，检查是否引入新问题 |
| 日志复用 | 已下载日志，无需重复下载 |

## 工作流程

```
Phase 0: 准备阶段 (Haiku Agent)
    ↓
Phase 1: 加载历史分析 (Sonnet Agent)
    ↓
Phase 2: 深度复查分析 (Opus Agent)
    ↓
Phase 3: 对比分析 (Opus Agent)
    ↓
Phase 4: 生成复查报告 (superpowers:writing-plans)
    ↓
Phase 5: 执行补充修复 (superpowers:execute-plan) [如有新问题]
```

## Phase 0: 准备阶段 (Haiku Agent)

**使用 Task 工具，model=haiku：**

```
准备复查分析环境：

1. 检查日志是否存在：
   - 检查 logjson/ 目录是否有 JSON 文件
   - 如果为空，返回错误提示用户先运行 /log-analytics

2. 统计日志信息：
   - 列出所有日志文件
   - 检查日志文件的修改时间
   - 报告日志是否过期（超过 24 小时建议重新下载）

3. 生成复查文档名：
   - 查找 server-game/docs/plans/ 目录下今天的复查文档
   - 格式：YYYY-MM-DD-XXX-log-analysis-recheck.md
   - 如果今天已有 001-recheck，下一个就是 002-recheck

4. 查找最近的原始分析文档：
   - 查找最近的 *-log-analysis.md（不含 recheck）
   - 返回文档名和路径

返回结果：
- 日志状态：存在/不存在
- 日志文件数量
- 日志时间范围
- 复查文档名：2026-01-31-001-log-analysis-recheck.md
- 关联原始分析：2026-01-31-001-log-analysis.md
```

## Phase 2: 深度复查分析 (Opus Agent)

**使用 Task 工具，model=opus：**

```
基于 logjson/ 目录现有日志进行深度复查分析：

## 已知上次分析结果
{Phase 1 返回的问题清单}

## 复查检测任务

### 1. 问题修复验证
对于上次分析中的每个问题，检查日志验证：

#### Critical 问题验证
逐个检查 Critical 问题是否已修复：
- 读取对应游戏的控制日志
- 检查问题字段是否正常
- 对比修复前后的数值变化

#### Medium 问题验证
...

#### Low 问题验证
...

### 2. 深度日志分析
首次分析可能遗漏的检查点：

#### RTP 异常检测
- 单个玩家 RTP 超过 200% 的记录
- RTP 持续低于 80% 的玩家
- RTP 波动异常大的玩家

#### 控制逻辑检测
- BOOST/SUPPRESS 切换频率是否正常
- Factor 值的分布是否合理（统计直方图）
- 控制决策与 RTP 是否匹配

#### FRTPG 检测
- FRTPG 触发率（各决策类型占比）
- CAPPED/REJECT 后的实际效果
- 重试次数分布

#### 时序分析
- 连续大奖检测（3 连胜以上）
- 异常投注模式
- 时间段分布

### 3. 新问题发现
检查是否有首次分析未发现的问题：
- 边缘情况
- 低频 Bug
- 性能问题
- 回归问题（修复引入的新问题）

## 输出格式

### 修复验证结果
| 原问题ID | 游戏 | 问题描述 | 修复状态 | 当前值 | 预期值 | 验证依据 |
|----------|------|----------|----------|--------|--------|----------|
| C1 | FortuneGems | FRTPG 未生效 | 已修复 | CAPPED 30% | >0% | 日志统计 |

### 新发现问题
| ID | 游戏 | 问题描述 | 严重程度 | 发现依据 |
|----|------|----------|----------|----------|
| N1 | Anubis | 乘数累积异常 | Medium | 日志分析 |

### 深度分析洞察
- RTP 分布统计（各游戏）
- 控制效果评估
- 系统健康度评分（优秀/良好/一般/需关注）
```

## 与 log-analytics 的关系

| 维度 | log-analytics | log-analytics-recheck |
|------|---------------|----------------------|
| 下载日志 | 是 | 否（使用现有） |
| 清理旧日志 | 是 | 否 |
| 首次分析 | 是 | 否 |
| 复查分析 | 否 | 是 |
| 对比分析 | 否 | 是 |
| 生成计划 | superpowers:writing-plans | superpowers:writing-plans |
| 执行修复 | superpowers:execute-plan | superpowers:execute-plan（可选）|

**典型工作流：**

```
1. /log-analytics        → 首次完整分析 + 修复
2. /log-analytics-recheck → 验证修复效果 + 补充修复
3. /log-analytics-recheck → 再次验证（可重复）
4. 如需新日志 → 回到步骤 1
```

## 常见问题

### Q: 什么时候用 recheck？什么时候用 log-analytics？

A:
- **用 recheck**：已有日志，验证修复效果或深度分析
- **用 log-analytics**：需要新采集日志，或首次分析

### Q: 如果日志太旧怎么办？

A: Phase 0 会检查日志时间。如果超过 24 小时，会提示建议先运行 `/log-analytics` 获取新日志。

### Q: 可以多次复查吗？

A: 可以。每次复查都会生成独立的序号文档（001-recheck, 002-recheck...），支持无限次复查。

### Q: 没有问题需要修复时会怎样？

A: Phase 5 会被跳过，直接报告复查完成和系统健康度评估。
